# AGENTS.md — workflow de travail demandé par Nicolas

Ce fichier décrit la procédure à suivre **à chaque évolution demandée**, sans
avoir besoin de la répéter.

**Principe clé : le serveur tourne en parallèle du travail.** Le serveur exposé
(https://mazurkiewicz1.zapto.org) tourne sur la **Raspberry Pi** (`~/lichess-mcp`
sur la Pi, déployé par `docker compose up -d --build` après chaque merge — voir §6)
et **jamais** depuis ce dépôt de travail. **Accès à la Pi : `ssh pi-mcp`** (alias
défini dans `~/.ssh/config` : HostName 192.168.2.3, User nicolas, IdentityFile
`~/.ssh/id_ed25519_pi`) — inutile de retenir l'IP ni l'utilisateur. On peut donc travailler
ici en parallèle (branches, tests, éditions, PR) sans affecter le serveur en cours ;
seuls les tests locaux (pytest, ruff, node) tournent à côté, sur des
ports/processus indépendants.

## 1. Branche dédiée

Toujours travailler dans une branche dédiée (ex. `feat/<sujet>-80ae23`),
jamais directement sur `main`.

## 2. Tests et documentation

- Réaliser des **tests pour chaque évolution** (pytest dans `tests/`, ex.
  `tests/test_evolutions.py`) et les documenter (docstrings explicites).
- Mettre à jour le `README.md` quand le comportement d'un outil change
  (signature, en-têtes PGN, horloge, bouton web...).
- Ne **pas** committer les notes brutes de la demande (ex. `prompt.txt`).

## 3. Sanitizers (à passer en local avant chaque push)

```bash
source .venv/bin/activate
ruff check .
node --test tests/web/util.test.mjs
npx eslint web/util.js tests/web/util.test.mjs eslint.config.mjs
LICHESS_MCP_STOCKFISH=/chemin/stockfish python -m pytest tests/ -q   # tests d'analyse
```

Notes :
- Les tests d'analyse nécessitent un binaire Stockfish (`LICHESS_MCP_STOCKFISH`
  ou `stockfish` dans le PATH ; en CI il est installé via `apt install stockfish`).
- La CI vérifie aussi que le serveur MCP démarre et expose les outils de base
  (check `fastmcp.Client(...).list_tools()` dans `.github/workflows/ci.yml`).

## 5. Push, PR, CI, merge

- **Numérotation `0.XX`** : la version du logiciel est `__version__` dans
  `server.py` (synchronisée avec `package.json`), au format `0.XX` (XX sur 2
  chiffres : 0.01, 0.02, … 0.10…). **Incrémenter XX avant chaque livraison sur
  main** — c'est-à-dire dans la branche de la PR, avant le push — pour que la
  version affichée dans le badge (coin haut gauche de l'UI web) et servie par
  `/web/api/version` corresponde exactement au merge déployé sur la Pi.

0. **Bug = issue d'abord** : si un bug est remonté (ou découvert en test) et
   qu'**aucune issue GitHub n'existe pour ce bug, la créer AVANT de commencer
   le correctif** (état `open`, titre explicite, description/repro). La branche
   de fix et la PR référencent ensuite cette issue (`#N` dans le titre ou le
   body de la PR) pour que le label `developped` soit posé automatiquement au
   merge (voir étape 5 ci-dessous). Aucun correctif de bug sans issue préalable.
1. Itérer en local jusqu'à ce que **tous les tests passent** et les sanitizers
   soient verts.
2. Pousser la branche (`git push -u origin <branche>`) et ouvrir une **PR** vers
   `main` (titre explicite, description des évolutions + tests effectués).
3. Corriger **tous les problèmes remontés par la CI** jusqu'au vert
   (rellire les check runs du PR).
4. **Merger la PR dans `main`** une fois la CI verte. Le dépôt est réglé avec
   `delete_branch_on_merge: true` : **la branche distante est supprimée
   automatiquement au merge** (plus besoin de nettoyer les anciennes branches
   à la main). En local, supprimer la branche fusionnée :
   `git checkout main && git pull --ff-only origin main && git branch -D <branche>`.
5. **Cycle de vie des issues — 4 états** :
   - **open** : issue à réaliser ;
   - **developped** : issue mergée dans `main` (PR validée) — le label
     `developped` est posé **automatiquement** au merge par
     `.github/workflows/label-developped.yml` (déclenché sur `pull_request:
     closed` quand la PR est mergée) ; **l'issue reste ouverte**, jamais
     fermée automatiquement ;
   - **deployed** : issue corrigée, validée par moi **et déployée sur la Pi** —
     label `deployed` posé **par moi via l'API** après le déploiement (§6) et
     sa vérification (HTTPS 200 + smoke test), avec un commentaire
     (« déployée en vX.YZ (commit …), site 200 OK ») ;
   - **closed** : correction **validée par Nicolas** (fermeture manuelle).
   Pratique : après un merge, je ne ferme **aucune** issue moi-même — je
   vérifie que `developped` est posé (workflow auto, sinon je le pose via
   l'API), puis après le déploiement Pi vérifié je pose `deployed` (avec un
   commentaire : version + commit + HTTPS 200 OK).
   C'est Nicolas qui ferme (`closed`) après validation.
6. **Connecteur MCP à mettre à jour** : si une livraison ajoute, renomme ou
   supprime un **outil MCP** exposé (ou change l'URL/auth du serveur), je dois
   le signaler **dans l'issue concernée ET dans le chat** — Nicolas doit alors
   recharger/mettre à jour le connecteur dans le Studio Mistral
   (procédure : `docs/DEPLOIEMENT.md` §5). À l'inverse, si aucun outil n'évolue,
   je le précise aussi (« pas de mise à jour du connecteur nécessaire »).

## 6. Déploiement sur la Raspberry Pi (production)

Après le merge dans `main` :

1. Mettre le dépôt local à jour :
   `git checkout main && git pull --ff-only origin main`
2. **Déployer sur la Pi** — le serveur exposé
   (https://mazurkiewicz1.zapto.org) tourne là-bas, pas depuis ce dépôt :

   - **Prérequis une fois pour toutes sur la Pi** : `sudo usermod -aG docker
     nicolas` (puis re-login SSH) pour utiliser le socket Docker sans mot de
     passe, et autoriser le push git sur la branche `main` du clone :
     `git config receive.denyCurrentBranch updateInstead`.
     Docker + Compose y sont déjà installés (dockerd actif, Caddy écoute 80/443).
   - Le **clone de production** vit dans `~/lichess-mcp` sur la Pi — on y
     accède simplement par **`ssh pi-mcp`** (alias `~/.ssh/config`, inutile de
     retenir IP ni utilisateur) ; `.env` et `Caddyfile` y sont hors git, donc
     jamais touchés par un push ; `data/` vit dans le volume Docker
     `games_data`. La Pi n'a **pas** de credentials GitHub : on pousse depuis
     ce dépôt via SSH.
   - Commandes de déploiement, depuis ce dépôt (`main` à jour) :

     ```bash
     # 1. sur la Pi : écarter les patches locaux non commités (volontairement
     #    non versionnés) pour garantir un push propre
     ssh pi-mcp 'cd ~/lichess-mcp && git checkout -- .'
     # 2. pousser main vers le clone de production (met à jour son worktree)
     git push ssh://pi-mcp/home/nicolas/lichess-mcp main:main
     # 3. rebuild du conteneur app sur la Pi — le commit courant est injecté
     #    dans l'image (ARG GIT_COMMIT, passé à `build` pas à `up`) et affiché
     #    dans le badge de version en coin haut gauche de l'UI (issue #67)
     ssh pi-mcp 'cd ~/lichess-mcp && docker compose build --build-arg GIT_COMMIT=$(git rev-parse --short HEAD) && docker compose up -d'
     ```

     `up -d --build` recrée **uniquement** le conteneur app (image rebuildée) :
     Caddy étant inchangé reste up et les ports 80/443 ne sont jamais libérés.
     Le nom de projet est figé (`name: lichess-mcp` dans `docker-compose.yml`),
     aucun `-p` nécessaire.

3. Vérifier que le site répond (**HTTPS 200** sur
   https://mazurkiewicz1.zapto.org) et faire un smoke test rapide si pertinent.

Le serveur n'est donc indisponible que quelques secondes (recréation du
conteneur app), jamais pendant le travail dans le dépôt principal. Le dossier
`DELIVERY/` n'est plus utilisé pour le déploiement.

## 7. Nettoyage après smoke test — règle absolue

Après un smoke test sur le serveur déployé, **ne supprimer QUE les parties que
j'ai moi-même créées pendant ce test** : je note les `game_id` renvoyés par mes
propres appels (`new_game`, `new_analysis_board`, `start_puzzle`, endpoints web
de création) et je ne fais `delete_game` que sur ces ids-là.

**Jamais** de boucle `list_games` + `delete_game` sur tout le serveur : les
parties/puzzles des utilisateurs (créés hors de ma session de test) doivent
rester intacts. Une partie est « à moi » uniquement si je l'ai créée dans la
session de test en cours.
